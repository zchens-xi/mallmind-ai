## 增量获取商品信息策略详解

### 📊 数据流转图解

```
用户请求商品推荐
        ↓
1. 检查同步模式
   ├─ 需要全量同步？ → 执行全量同步策略
   └─ 正常模式 → 继续增量同步
        ↓
2. 获取上次同步时间
   ├─ Redis可用 → 从缓存获取时间戳
   └─ Redis不可用 → 使用默认2小时前
        ↓
3. 执行增量查询
   SQL: SELECT * FROM pms_product 
        WHERE modify_time > #{lastSyncTime}
        AND delete_status = 0 
        AND publish_status = 1
        ORDER BY modify_time ASC, id ASC
        ↓
4. 数据补充策略
   增量数据足够？
   ├─ 是 → 直接返回增量数据
   └─ 否 → 补充热门商品
        ↓
5. 更新同步时间戳
   将最新商品的modify_time保存到Redis
```

### 🎯 具体策略细节

#### 策略1: 时间戳管理
- **Redis Key**: `product:sync:timestamp`
- **存储格式**: Long类型时间戳
- **过期时间**: 7天（防止垃圾数据堆积）
- **兜底机制**: Redis不可用时，默认获取最近2小时数据

#### 策略2: 增量查询逻辑
```sql
-- 实际执行的SQL示例
SELECT * FROM pms_product 
WHERE modify_time > '2024-01-19 14:30:00'  -- 上次同步时间
  AND delete_status = 0                     -- 未删除
  AND publish_status = 1                    -- 已发布
ORDER BY modify_time ASC, id ASC           -- 时间升序，确保连续性
LIMIT 100;                                 -- 分页限制
```

#### 策略3: 多级补充机制
1. **优先级1**: 增量数据（基于modify_time）
2. **优先级2**: 热门商品补充（基于销量）
3. **优先级3**: 兜底基础商品（基于ID）

#### 策略4: 全量同步触发
- **触发条件**: Redis中存在 `product:full:sync:flag = true`
- **执行策略**: 获取最新的商品，按modify_time降序
- **完成清理**: 自动清除全量同步标记

### 🚀 实际执行流程示例

假设现在是 2024-01-19 16:00:00

```java
// 1. 获取同步时间
Date lastSyncTime = getLastSyncTime(); 
// 返回: 2024-01-19 14:30:00 (从Redis获取)

// 2. 执行增量查询
List<ProductInfo> products = getIncrementalProducts(lastSyncTime, 50);
// 查询结果: 找到12个在14:30:00之后修改的商品

// 3. 数据不足，补充热门商品
if (products.size() < 50) {
    List<ProductInfo> hotProducts = getHotProducts(38); // 50-12=38
    // 去重合并
    products.addAll(hotProducts);
}

// 4. 更新同步时间
updateSyncTime(new Date()); 
// 更新Redis: product:sync:timestamp = 2024-01-19 16:00:00
```

### 📈 性能优势对比

**原有方式**:
```sql
-- 每次都查询全量数据
SELECT * FROM pms_product 
WHERE delete_status = 0 AND publish_status = 1
ORDER BY sort DESC, sale DESC
LIMIT 100;
```
- 每次扫描全表
- 数据量大时性能差
- 缓存命中率低

**新增量方式**:
```sql
-- 只查询变更数据
SELECT * FROM pms_product 
WHERE modify_time > '2024-01-19 14:30:00'
  AND delete_status = 0 AND publish_status = 1
ORDER BY modify_time ASC
LIMIT 50;
```
- 只扫描增量数据
- 利用modify_time索引
- 大幅减少IO开销

### 🛡️ 容错机制

1. **Redis故障**: 自动降级到时间策略
2. **增量数据为空**: 自动补充热门商品
3. **查询异常**: 使用兜底基础商品列表
4. **时间戳异常**: 重置为默认时间

### 📊 监控指标

```java
// 获取同步统计
Map<String, Object> stats = getSyncStats();
// 返回:
{
    "lastSyncTime": "2024-01-19 16:00:00",
    "needFullSync": false,
    "incrementalCount": 12  // 自上次同步以来的变更数量
}
```

这个策略的核心优势是：
1. **智能化**: 根据数据变更情况自动调整策略
2. **高效性**: 只同步变更数据，大幅提升性能
3. **可靠性**: 多层容错机制保证服务稳定
4. **灵活性**: 支持增量和全量两种同步模式
